Tess-built rooms

The app becomes a player and a room becomes a document. You say what you want, Tess writes the change, and the phone draws it straight away. Nothing installs unless a brand-new kind of part has to be born.

This is design only; nothing is built yet. It starts as one experimental room, working name Chart room: the room where a navigator draws. The polished rooms stay as they are. Research notes with every source are in the repo at docs/design/tess-built-rooms/research.md.

The shape

Every system that has done this in production uses the same split. Airbnb, Lyft, Shopify, Yandex's DivKit, Flutter's remote widgets and Google's A2UI all work this way. The phone owns a fixed kit of native parts, a document composes them and binds them to data, and anything beyond composing runs in a sandboxed interpreter. Tessera already has the first half: fixed places on every screen, rooms that only hand data to them, and a look catalog Tess can turn by voice.

Four tiers, picked by the size of the change

Why tier 3 still needs an install: an iPhone only loads native code that was signed when the app was installed, and it gives apps no JIT. Apple's own engineers confirm this, and it holds even in Developer Mode. Scripts, wasm, shaders and data are all allowed to arrive later. That is why tier 2½ exists: it moves most "code" changes onto the no-install side. Each new part that lands also widens the kit for good, so installs get rarer over time.

From one sentence to the screen

"Make the plant list calmer and glow the thirstiest one"

  1. Read. Tess takes the sentence along with the room document, what you last touched (anything within 30 seconds counts as "this"), and the kit's own description of itself, which the app generates from code.
  2. Plan, then patch. She thinks in plain words first, then emits a small strict patch. Strict formats make models reason worse, so planning stays free and only the output is constrained. "Calmer" is a step on the motion trait. "Glow the thirstiest" is a reaction plus a look.
  3. Check. Three gates. Shape: the schema. Sense: the engine's validator, the same pattern the class builder uses. Sight: the phone renders the change offscreen at the largest type in both themes and checks overlap, contrast, tap size and cut words. A failure retries once, quietly.
  4. Show a ghost. The change appears in place, faint. A small change sets after the 2-second drying line. Anything that widens what the room can touch waits for its own tap.
  5. Keep history. The patch is an op group in the log. "Undo", "go back to this morning's version" and "what changed?" all work, and so does undo of an undo.

The room document

The document is a flat list of parts linked by ids rather than a deep tree, because models write flat lists more reliably (A2UI's finding). Data is bound by path and never copied in. New ideas, past the prior art



  
Rooms are objects too
A room document is stored as objects in the engine, with a class, links and history, so UI is as linkable, searchable and undoable as your data. "Last Tuesday's version of this room" becomes a query, and you can link a note to the room it describes.
From Smalltalk's live objects, without its unversioned state

  
Speak in traits, finish with your thumb
Small changes move along named axes (density, size, motion, weight) rather than raw numbers, so they survive a theme swap. After each spoken change, the axis that moved stays under your thumb for a few seconds, so "a bit calmer" can be finished by feel.
Look catalog plus Bret Victor's "immediate connection"

  
Ghost variants for vague asks
"Make it nicer" produces two or three ghosts stacked in place. You swipe through them and keep one. What you keep becomes local taste data, which the small on-device model uses to rank the next set of variants.
Galileo and Stitch variants, turned into a learning loop

  
Facts and wishes, so every reaction has a because
Parts never call each other. They post facts ("Orchid: 6 days since water") and wishes ("glow the thirstiest"). You can ask Tess "why is that glowing?" and she traces it. The Mac can replay a week of real facts against a new room version as a test drawn from your own life.
Dynamicland's Claim, Wish, When; HyperCard's message path

  
A reach line
Each part declares what it may touch: read a class, write a class (always as a pending, undoable group), a timer, a haptic. When an edit widens the room's reach, a separate line says so ("can now mark plants watered") and needs its own tap. Money writes are never grantable to a room, and the key never enters a document.
Object capabilities (WASI, MCP Apps' bridge)

  
Signed packs, and the weekly install as a release train
Logic packs and shader libraries are signed by the Mac with a key whose public half ships in the app. The phone runs only what verifies. Brand-new parts batch up for the build that goes out with the profile refresh anyway.
React Native's over-the-air split, applied to wasm and Metal

  
Paths become roads
The phone notes which compositions, scripts and shaders you keep. The Mac proposes promoting the well-worn ones into native parts under the same name, so a room gets faster and more polished on its own while its document stays the same.
A tracing JIT, at the level of product rather than machine code

  
Copy a room like a prototype
"Like the Galley, but for my plants" copies a room's document and rebinds it to another class, without starting from a template. It is how the preset rooms eventually become editable: each one is rewritten as a document the player renders exactly as it does today.
Self's prototypes; Embark's dynamic documents

Risks and what isn't verified


    

  • SwiftUI's shader effects take only a precompiled metallib. Whether a metallib downloaded after install loads on a real device is unverified, and R4 starts by testing it. If it doesn't load, on-phone shaders draw through a Metal view instead.
    • 

  • WasmKit speed on the phone is unverified. The interpreter is many times slower than native, which is fine for reactions and too slow for drawing; drawing stays native.
    • 

  • Free developer profiles expire every 7 days. The release-train idea relies on that refresh anyway.
    • 

  • The older Build with Tess page (stretch 3) said Claude never writes code or screens. Your ask today supersedes it for this room. Its privacy section is already superseded by your rule this morning: everything may go to Claude except the key.
